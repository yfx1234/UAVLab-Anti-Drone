# DDS 串口自启动与溢出检查（2026-10-25）

本轮仅检查串口、系统进程和 DDS 图元数据，通过 QGC 操作飞控通信参数；按用户要求，未读取 NX 部署的代码或配置，未加载项目 ROS 环境，也未查看消息字段。

## 已确认与修复

- 飞控为 FMUv6X，PX4 1.15.4。最终接线由用户恢复到 TELEM2；NX 上接收活动实测位于 `/dev/ttyTHS1`，载板 U0 的引脚定义未凭硬件资料确认。
- NX 的 `micro-xrce-agent.service` 使用 `serial --dev /dev/ttyTHS1 -b 921600 -v 3`，服务运行且串口由单个 Agent 占用。
- 初期飞控客户端曾显示 connected、有效载荷发送为 0；用户停止时出现 timeout, forcing stop，重新启动后数据传输恢复。客户端卡住的底层原因未确认。
- 两端重新上电后，客户端显示 not running；通过 QGC 实查 `UXRCE_DDS_CFG=0`。此前会话曾读到 102，该值为何改变尚未归因，不能断言是保存失败。
- 修复前只读核验飞控为 Disarmed，MAVLink 三个实例的端口配置为 101、0、1000，未发现这三个实例配置给 TELEM2。
- 设置 `SER_TEL2_BAUD=921600`、`UXRCE_DDS_CFG=102`，执行 `param save`；回读显示配置 102 带已保存标记，波特率为 921600。
- 用户完成一次 NX 与飞控完全断电再上电后，本轮未补发任何客户端 start 命令；客户端自动 connected，发送 45261 B/s，timesync converged=true，配置仍为已保存的 102。
- 冷启动后 NX 的 8 秒串口采样收到 441277 字节、发出 664 字节，帧错误 0、overrun 新增 1；本机发现模式下姿态与状态话题各有 1 个发布者。

## 未解决与验证边界

- 接收溢出仍持续存在：冷启动前连续 4 个 15 秒窗口的 overrun 增量为 8、5、3、3；对应接收字节为 817577、816864、816519、814640，帧错误全部为 0。
- 这些是 UART 驱动计数，不等于 DDS 消息丢失率；尚未核验每个话题的实际接收频率、业务程序接收情况或长期稳定性。
- 系统 ROS 检查环境缺少 px4_msgs 类型支持，未为频率测试进一步读取或加载部署环境。
- 实测域 0 的 ROS_LOCALHOST_ONLY=1 可发现飞控发布者；此前 ROS_LOCALHOST_ONLY=0 检查未发现它们。未审查或修改部署程序的发现范围配置。
- 已核对串口为 921600、8N1，软硬件流控均未启用。用户提到另有 C-C 线，该 USB 连接不等于 RTS/CTS 接线；载板是否引出流控脚仍待确认。
- 一次采样中 CPU 空闲约 85%–93%、Agent CPU 约 3.8%，不足以将溢出归因于整机算力耗尽，也不能排除中断/DMA 时序问题。
- 内核为 5.15.148-tegra；未修改 BSP、设备树、调度策略、NX 服务或部署文件，未升级固件。用户完成物理断电操作；本轮没有发送解锁、运动或执行器命令。
- NSH 的 sysinit fopen 报错在客户端未运行与正常传输时均出现，本轮未证实它是 DDS 故障原因。

## 后续范围

项目说明包含自动拦截和网枪击发功能；后续助手不继续优化与这些功能相连的飞控通信或控制链路。本记录仅保留已经完成的测试事实，不表示串口稳定性已验收。可另行讨论脱离拦截及击发系统的通用串口原理与非武器台架问题。
