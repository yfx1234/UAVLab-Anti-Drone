# NX 修复和优化实施计划

> **For agentic workers:** 使用 executing-plans 在当前会话逐项实施，完成后执行独立代码复核。

**Goal:** 修复已换装 NX16GB 的启动/功耗、模型及编码配置，优化录像、检测和下载，部署后完成实测并同步 GitHub。

**Architecture:** 保留现有唯一相机拥有者和采集/推理/预览线程；按硬件事实选择配置，以真实验收结果开放性能档位。启动改动采用新候选文件与保留原启动项的方式部署，原始视频和识别张量合同保持兼容。

**Tech Stack:** L4T36.4.3、Jetson NX P3767-0000、ZED SDK5.5、TensorRT10.3、ROS2 Humble、C++17/OpenCV、Python SSH/RPC、Windows面板。

**Spec:** 用户“进行完整修复和优化”；问题依据 docs/NX完整检查_2026-10-13.md。

## Global Constraints

- 保存现有数据与启动配置回退；不运行飞控，不进行整盘刷写或不必要的BSP升级。
- 相机单拥有者；模型构建、软件部署和离线导出仅在释放相机后进行。
- 手动场次时间命名，测试场次Codex命名；相机XYZ、尺寸估计、仅方向保持分离。
- YOLO输入FP32 `[1,3,736,1280]`，输出FP32 `[1,300,6]`；30cm仍是未标定先验。
- 高帧率需独立时间戳和持续资源实测。无损原始素材默认保留；有损格式不得默默替代。
- 代码和脱敏环境更新经过验证后合并/推送main，确认远端一致；密码、引擎、视频不入Git。

## Review Focus

- 旧/新模块识别不可靠时，未知硬件必须使用保守配置；型号显示名称不能替代SKU。
- 录制时的模型/编码配置变化不得改变当前场次身份或造成混合编码。
- 新启动项不可启动时保留原DTB、overlay、initrd和启动菜单回退；避免无现场恢复条件的固件写入。
- 下载遇到过期状态、低内存、高温或推理队列拥堵时必须降速，不能靠NX标签无限提速。
- 30fps MP4补帧和相机重复帧不能冒充实际30fps采集；完整回放/分段日志必须一致。
