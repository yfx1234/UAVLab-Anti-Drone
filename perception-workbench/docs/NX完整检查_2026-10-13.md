# NX 16GB 完整检查记录（2026-10-13）

## 结论与范围

已确认换装 Orin NX 16GB，原载板、NVMe、用户、图传地址与项目目录继续可用。现有感知程序可运行，相机、YOLO、通用检测、SVO 无损录像、RGB/深度视频导出及电脑面板图传均完成短时验证。**系统迁移尚未完成，30 fps 无损录像未达标。**

## 硬件、启动和环境

- EEPROM 模块料号 `699-13767-0000-303 G.1` 对应 P3767-0000 / Orin NX 16GB；Linux 可见内存约15.29 GiB（保留内存后），8个CPU在线，CUDA初始化成功、8个SM、SM8.7。设备树的“Orin NX”显示名称在旧 Nano 上也存在，不能单凭该名称识别模块。
- 根分区仍为 NVMe，233 GiB总容量、审计开始约133 GiB可用；新增测试素材约3.14 GiB。
- Ubuntu22.04.5、内核5.15.148-tegra、L4T36.4.3、CUDA12.6、TensorRT10.3.0.30、ZED SDK5.5.0、ROS2 Humble。按正式启动脚本 source ROS/工作区后，程序的动态库全部找到；裸 SSH 环境下 `ldd` 缺 ROS 库不代表安装损坏。
- QSPI启动固件报告36.4.4；根文件系统和核心包为36.4.3。GStreamer、multimedia-api及DLA编译器包为36.4.7。这是需整理的版本混用，尚无证据证明某一差异单独导致当前所有问题；不要直接执行全系统升级。
- `extlinux` 默认仍为 `ZED_DAMIAO`，FDT为 Nano `p3767-0003` 的 Seeed J401 DTB，活动 `compatible` 同样含 `p3767-0003`；不是完整的 NX 匹配启动配置。
- `/etc/nvpmodel.conf` 仍指向 `nvpmodel_p3767_0003_super.conf`，当前ID2名称MAXN_SUPER属于Nano配置。该文件只定义CPU0–5，实际CPU0–7在线；TPC掩码配置240而实际15。名称并不能证明功耗设置正确。系统已含NX0000普通/Super配置文件，但不能只换模式数字，须与载板和启动固件一起核对。

## 相机和感知链路

相机链路为 GMSL → ZED Link Mono → CSI0 / I2C10 → ZED SDK → 唯一相机线程。板上 `zedx`、MAX9296、MAX9295实际驱动版本1.4.4，CAM0 reset高电平配置有效，video0/video1已出现，SDK成功打开1920×1080左右校正图。

先前“启动中”日志显示SDK正在为新GPU优化 `neural_depth_light_5`，到100%后相机打开成功；本次后续启动成功。因此不能把首次初始化等待归为相机掉线。Argus启动日志仍有PIX_SHORT、AlreadyAllocated及Wrong frequency range信息；短测无新增应用级错误，但这些驱动告警需在匹配NX启动配置后继续复核，不能直接认定全都无害。

默认RGB不运行识别；开启YOLO或通用检测才计算深度。YOLO输入仍是宽1280×高736，原图是1920×1080。通用检测使用原图对比度候选与连续跟踪，图像同步IMU运动数据本次有效。所有定位仍输出相机光学坐标：X右、Y下、Z前，单位米；有效深度、30cm尺寸估计、仅方向分别标识。

现用引擎与Nano版本SHA256相同，合同检查和3次零输入推理通过，但TensorRT输出跨设备警告。**暂时能运行，不代表NX引擎已适配**；应在NX上从现有ONNX重新构建，并校验输入FP32 `[1,3,736,1280]`、输出FP32 `[1,300,6]`，再比较同一SVO识别结果。现有PT/ONNX不需仅因换核心重新训练。

57份板上源码与仓库一致；仅板上README仍为历史完整跟踪方案、Nano YAML注释过时，运行参数与当前源码相同。电脑日常面板源码一致，差异是仓库保留的历史面板文件。程序不需要因更换NX重写整体感知流程。

## 必须调整与建议顺序

1. **启动/功耗配置**：准备同L4T版本、实际DAMIAO载板、NX P3767-0000匹配的基础DTB/BSP，合并并复核已验证的CSI0、PH6 reset、I2C10和ZED Mono适配。备份现有extlinux、DTB/DTBO、initrd与QSPI信息，保留回退启动项，在可恢复现场做受控重启验收。不要直接换成NVIDIA开发套件DTB或仅改文件名。
2. **NX TensorRT引擎**：相机释放后用原ONNX构建独立候选、生成新SHA256/manifest、验证张量合同与同场SVO识别，再选择为默认；原引擎保留回退。
3. **硬件编码与包一致性**：在匹配NX配置下整理同一BSP的多媒体包，验证1080p30合成帧编码、文件尾完整性、SDK SVO回放与原图质量，再决定是否新增可选编码模式。H264/H265通常有损，不能悄悄替换训练素材的LOSSLESS默认。
4. **软件环境描述**：supervisor的设备信息仍硬编码 `nano_lossless`、`nx16_ready=False`、SDK5.5；NX YAML为占位，默认入口实际上由supervisor命令行启动。应增加事实性硬件/版本检测与独立性能验收状态，而不能简单改为“NX已准备好”。下载在检测/录像时仍沿用Nano的256KiB/s保护，NX上也未自动升档；需在最终配置下验证并按资源动态调整。
5. **性能验收**：稳定1080p15作为当前默认。迁移后重测RGB、YOLO、通用、联合、LOSSLESS录像、图传及并行下载，至少10–30分钟并检查60秒分段边界、独立时间戳、掉帧/跳帧、温度、内存和磁盘。30fps可先用于纯RGB短测，不能作为当前无损录像保证。
